📌 한눈 요약

두 앱의 토양 접수 화면은 약 95% 동일합니다. 접수 폼·목록(22컬럼)·공익직불제 뷰어/일괄적용·통계·검색·다크모드·라벨인쇄, 그리고 엑셀 가져오기 모달(soil-result-importer.js)·서식 모듈(excel-import-manager.js)은 바이트 단위로 동일합니다. 차이의 대부분은 ① 아키텍처 분기(메인=BaseSampleManager 중심, soil=순수 모듈 추출)와 ② 봉화군 전용 vs 전국 배포 전제에서 비롯됩니다.

핵심 비대칭: soil은 분석결과 IndexedDB 저장·전국 주소·산 토글·순수 모듈화가 앞서고, 메인은 클라우드 동기화 견고성(fromCache 가드·재시도·삭제 확인)이 앞섭니다. → 동기화는 단순 일방향이 아니라 양방향 선별 포팅 대상입니다.

11이식 후보 종합 (우선순위)

⭐ soil → 메인 (가져올 기능)

우선후보내용 / 적용 시 고려
P1산(山) 토글 버튼필지 주소 옆 토글 + 자동완성 산 자동 동기화. 순수 UX, 위험 낮음. 메인 체크박스 대체.
P1AnalysisDB (IndexedDB)흙토람 검정결과를 Dexie/IndexedDB 주저장 + LS 백업 + 자동 마이그레이션. localStorage 5MB 한계 해소. dexie 의존성 추가 필요.
P2탭 인지 통계 + 엑셀 내보내기현재 경지구분 탭 기준 집계/내보내기 + '경지구분1차' 컬럼. 동작 변경이라 사용자 확인 권장.
P3전국 주소(SIDO SSOT, 17개 시·도 약어)주소 복사/내보내기 정확도. 봉화 운영엔 영향 작음. 위험 낮음.
P4basePnu 가져오기 필드공익직불제 BASEPNU 보존. 공익직불제 import 사용 시에만 의미.
P4순수 모듈 추출(reception-group·soil-log-record)코드 품질·단위테스트성. 산출물 동일이라 가치 중간.
참고전국 자동완성(regionKeys:null)봉화 전용 메인엔 이식 비권장(범위 정책 충돌). 정책 결정 필요.

🟪 메인 → soil (역포팅 권장)

우선후보내용
P1동기화 견고성 (SAMPL-1-80)fromCache 가드·mergeCloudData·getAllWithMeta·멱등 삭제·smartMerge allowDeletions. soil 오프라인 데이터 유실 리스크 완화.
P2클라우드 동기화 실패 복구_handleCloudSyncFailure + 온라인 복귀 재시도 + 배너. soil은 토스트만.
P2그룹수정 삭제 확인(SAMPL-1-82)빈 필지/작물로 인한 조용한 삭제 전 confirm + 취소 시 롤백.
P3persistRecords 추상화 / landClass1 동적생성 / firestore false-resolve 감지코드 일원화·유지보수성.
🔑 동기화 대원칙 ① 두 프로젝트는 독립 Firebase·독립 버전·독립 배포 — 설정 파일 교차 복사 금지.
② soil은 순수 .js (TS 아님) — sample-log-electron-test의 TS 마이그레이션과 무관, .js 의미 단위 동기화.
③ 아키텍처 성숙도 역전 → 통째 복사 금지, 양방향 선별 포팅만.
④ soil 전용 파일(analysis-db·reception-group·soil-log-record·main-stats) 및 메인 동기화 가드는 서로 덮어쓰지 말 것.

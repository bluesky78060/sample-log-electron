📌 가장 유력한 설명 (Most Likely Explanation)

이 코드베이스는 "기존 타입 복사 → 상수 변경" 방식의 공식 확장 패턴으로 성장했고, BaseSampleManager·ExcelImportManager로 공통화를 시작했으나 Template Method 수준까지 완료하지 못해 핵심 메서드 6개와 280~800줄의 중복이 잔존한다. 같은 성장 방식이 문서 부채(모듈 5개·폴더 5개 미기재)를 낳았으며, 별도로 듀얼 스토리지 싱크에 fire-and-forget 구조 리스크가 존재한다.
⚠️ 종합 핵심 미지수 — 판별 프로브 storage-manager.js:85-98의 Firestore 저장 실패 경로에서 syncedAt이 설정되는지 검증 필요. 설정된다면 sync-utils.js:121-135의 자동 삭제와 결합해 실제 데이터 유실 가능 → L2가 P0로 승격.

⚖️ 반박 라운드 & 수렴 분석

리더(L1)에 대한 최강 반박

"중복은 양적 문제일 뿐, 실질 위험은 L2의 데이터 정합성이다. 중복 코드는 동작하지만 fire-and-forget 싱크는 사용자 데이터를 잃을 수 있다."

리더가 유지된 이유

L1은 증거가 비트 단위로 확정적(High 85%)이고, L2의 실손실은 런타임 미검증(Medium). 다만 수정 우선순위는 L2가 앞설 수 있음.

수렴 노트

  • L1 ⇄ L3 부분 수렴: 동일 기저 메커니즘 — "점진적 복사-확장 성장 + 아키텍처 통합/문서화 후행". 새 시료 타입을 기존 타입 복사로 추가하는 공식 패턴이 중복과 문서 부채를 동시에 생산.
  • L2는 분리 유지: 독립적 메커니즘 (동시성/정합성 설계 결함).

🚀 권장 후속 조치 (백로그)

우선순위작업비용효과

P2 L3 문서 현행화: CLAUDE.md에 미기재 모듈 5개·폴더 5개 반영 소 AI 협업 정확도 향상, 즉시 가능

# SAMPL-1-153 플랜 리뷰

## ⚠️ 플랜 리뷰를 수행하지 않았다 (정직한 기록)

`critic` 에이전트 플랜 리뷰를 **실행하지 않았다.** 하지 않은 검증을 했다고 기록하지 않는다.

**사유**: 사용자 지시 — "코드 수정이나 중요가 낮은 작업은 플랜리뷰하지말고 진행해줘" (이 세션). 이 티켓은 코드 수정이다.

## 생략을 정당화하는 근거

| 근거 | 내용 |
| --- | --- |
| 결함·원인·수정 지점이 이미 확정됨 | 적대적 검증이 재현까지 마쳤다. 설계 선택지를 탐색하는 단계가 아니다 |
| 검증된 선례가 있다 | 테스트 프로젝트 커밋 `4fbce64`에서 같은 결함을 같은 방식으로 수정하고 단위 55건 + E2E 14건 + 변이 검증으로 확인했다. 이 티켓은 그 이식이다 |
| 기존 패턴을 따른다 | `soil-result-importer.js`는 이미 자동매핑을 모듈 레벨 순수 함수 + `_fns` 노출로 단위 테스트한다. 새 구조를 도입하는 것이 아니다 |
| 검증이 기계적 | "미리보기 번호 = 실제 저장 번호"를 시나리오별로 실측한다. 판단이 아니라 대조다 |

## 그래도 남는 리스크와 대응

1. **양쪽 중 한쪽만 고치는 것** — 이 결함이 정확히 그렇게 생겼다(폼 경로는 성토 분기를 쓰는데 가져오기 경로만 빠뜨렸다).
   → 3개 시나리오에서 미리보기와 실제 저장을 **나란히 출력해 대조**한다. 매니저 분기를 되돌리는 변이 검증으로 테스트가 실제로 잡는지 확인한다.

2. **두 규칙의 드리프트** — 미리보기 쪽 `collectExistingNumbers`와 매니저 쪽 `computeNextNumber`가 어긋나면 같은 결함이 재발한다.
   → 두 함수를 한 줄씩 대조하고 그 대응을 주석에 남긴다. 코드 리뷰에 대조를 명시적으로 요청한다.

3. **운영 코드 리팩터링 범위 초과** — 순수 함수 추출이 의도치 않게 동작을 바꾸는 것.
   → 추출은 로직 이동만 하고, 성토 분기 외의 동작 변경은 하지 않는다. 기존 E2E 210건 회귀 없음을 확인한다.

4. **약한 단정으로 또 새어나가는 것** — 테스트 프로젝트에서 75건이 전부 통과하는 상태로 이 결함이 새어나갔다.
   → 메모리 배열이 아니라 `localStorage`를 읽고, 유일성과 **실제 번호값**을 정확 일치로 단정한다.

## 코드 리뷰와 적대적 검증은 생략하지 않는다

P1 데이터 무결성 결함이고 운영 코드다. 구현 후:
- `code-reviewer`(opus) — 두 규칙 대조를 명시적으로 요청
- 적대적 검증(`critic`, "이 변경을 반증하라") — 1차 리뷰가 이 결함을 놓쳤던 선례가 있으므로 반드시 수행

생략한 것은 **플랜** 리뷰뿐이다.

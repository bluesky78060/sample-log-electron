# SAMPL-1-153 방향 — 성토 행 엑셀 가져오기 접수번호 결함

- 분류: **운영 데이터 무결성 버그**, 우선순위 1
- 발견 경로: SAMPL-1-124(테스트 프로젝트 포팅) 적대적 검증

## 목표 (Why)
운영 중인 앱에서 **구분이 '성토'인 행을 엑셀로 가져오면 전 행이 같은 접수번호로 저장된다.** 미리보기는 1, 2, 3을 보여주지만 실제로는 1, 1, 1이 들어가고, 이후 일반 접수의 자동채번이 영구히 1번에 고정된다.

접수번호는 이 제품의 **1차 식별자**다 — 라벨 인쇄, 흙토람 내보내기, 대장 출력이 모두 이 값을 쓴다. 경고 없이 중복 대장이 만들어지고 복구는 전 건 수동 재번호다.

## 사용자 (Who)
봉화군 농업기술센터 담당자. 성토 시료를 엑셀로 일괄 접수하는 경우.

## 범위 (What)

**두 곳을 모두 고쳐야 한다.** 한쪽만 고치면 미리보기만 맞고 저장은 그대로다.

| 파일 | 문제 |
| --- | --- |
| `src/soil/soil-script.js:853-856` | `addImportedRecord`가 성토 분기 없이 일반 채번만 호출 |
| `src/soil/soil-result-importer.js` `_existingNumbers`/`_recompute` | 들어오는 행의 성토 여부를 판정하지 않아 일반 시퀀스 번호를 찍는다 |

### 결함 연쇄
1. 성토 행에 일반 시퀀스 번호(`1`)가 찍힌다
2. 저장된 레코드는 `subCategory='성토'`이므로 다음 호출에서 `computeNextNumber`가 일반 체계(`fill=false`)로 계산하며 **이 레코드를 제외한다**
3. 카운터가 전진하지 않아 다음 행도 `1`을 받는다 → 1, 1, 1…
4. 가져오기 후 일반 접수를 새로 등록해도 다음번호가 계속 `1`이다

`generateNextFillReceptionNumber`(`:814`)가 이미 있고 폼 등록 경로(`:2042`, `:3674`, `:3687`)는 올바르게 쓴다. **가져오기 경로만 빠뜨렸다.**

## 제약
- 운영 코드다. 대규모 리팩터링보다 **결함 경로를 정확히 고치고 회귀를 테스트로 잠그는 것**이 우선
- `window.ReceptionNumber.computeNextNumber`의 분류 규칙(성토/일반 분리, `F` 접두 제외/제거)과 미리보기 쪽 규칙이 **한 줄씩 같아야** 한다 — 어긋나면 같은 결함이 다시 난다
- 커밋 시 `docs/`를 소스와 함께 넣어야 한다 (v1.17.7 사고 → SAMPL-2-22)

## 우선순위
P1. 운영에서 살아 있고 데이터 무결성을 조용히 깨뜨린다.

## 리스크
- **미리보기만 고치고 매니저를 빠뜨리는 것** — 실제로 이 결함이 그렇게 생겼다. 양쪽 수정 후 "미리보기 번호 = 실제 저장 번호"를 시나리오별로 실측한다
- 일반 `5`와 성토 `F5`를 충돌로 오판하는 것 — 두 시퀀스는 독립이다
- 수동 접수번호가 섞인 배치에서 커서가 어긋나는 것

## 완화 (기존 사실)
Firestore docId는 `log.id`(UUID)이고 분석결과도 logId 키라 **클라우드 덮어쓰기나 분석결과 오결합은 없다.** 목록에 즉시 보이므로 탐지는 빠르다.

## 검증
- 성토만 / 일반·성토 혼재 / 수동 성토번호 + 자동 혼재 3개 시나리오에서 미리보기 = 실제 저장, 중복 0
- 기존 레코드(일반 `7` + 성토 `F4`) 시드 상태에서 다음 번호가 `8` / `F5`
- **변이 검증** 필수 — 매니저 분기를 되돌리면 테스트가 실패해야 한다
- 접수번호 단정은 `not.toBe('')` 수준으로는 이 결함을 못 잡는다. 테스트 프로젝트에서 **75건이 전부 통과하는 상태로 새어나갔다** → 유일성과 실제 번호값을 단정한다

## 방향 확정
플랜 리뷰는 **생략한다** — 사용자 지시("코드 수정이나 중요가 낮은 작업은 플랜리뷰하지말고 진행"). 다만 P1 데이터 무결성이므로 **코드 리뷰와 적대적 검증은 생략하지 않는다.** 생략 사실은 `SAMPL-1-153-plan-review.md`에 기록한다.

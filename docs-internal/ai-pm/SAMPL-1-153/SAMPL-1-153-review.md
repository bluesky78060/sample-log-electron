## 고친 결함

구분(`subCategory`)이 '성토'인 행을 엑셀로 가져오면 **전 행이 같은 접수번호로 저장**되고, 이후 일반 접수의 자동채번이 영구히 1번에 고정됐다.

```text
미리보기: 1, 2, 3
실제저장: 1, 1, 1      ← 유일 1/3
저장 후 일반 다음번호: 1
```

접수번호는 이 제품의 1차 식별자다(라벨 인쇄·흙토람 내보내기·대장 출력). 완화 요소: Firestore docId가 `log.id`(UUID)이고 분석결과도 logId 키라 클라우드 덮어쓰기·분석결과 오결합은 없었다.

**원인**: 성토는 `F` 접두의 별 시퀀스이고 `generateNextFillReceptionNumber`(`soil-script.js:814`)가 이미 있는데 **가져오기 경로만 빠뜨렸다**(폼 경로 `:2042`·`:3674`·`:3687`은 올바르게 쓴다). 저장된 성토 레코드는 `computeNextNumber`의 일반 체계(`fill=false`)에서 제외되므로 카운터가 전진하지 않는다.

## 1차 코드리뷰 (APPROVED)

리뷰어가 무작위 로그 4,000세트로 `computeNextNumber` ↔ `collectExistingNumbers`를 **16,000회 차분 대조** → 불일치 0. 요청한 "두 규칙이 한 줄씩 같은지"를 실측으로 답했다. `_recompute` 순수화도 필드 단위 대조로 의도치 않은 동작 변경 없음을 확인.

지적 🟡3건 중 2건(기본 경지구분 폴백 누락, 저장 키 문자열 복제)은 `e16bb7b`에서 반영, 1건(성토 F 없는 수동 번호 계약)은 SAMPL-2-30.

**우려 해소**: 미리보기가 `generateNextFillReceptionNumber`를 호출해 매 재계산마다 로그를 찍는 문제는 **프로덕션에서 발생하지 않는다** — `this.log`가 `debug` 게이트 안이고 `window.DEBUG`는 `localStorage.DEBUG_MODE==='true'` 또는 개발 모드에서만 true다.

## 🟠 적대적 검증이 찾은 회귀 (핵심)

**1차 코드리뷰가 APPROVED를 낸 뒤에** 적대적 레인이 찾았다.

순수화가 자동채번을 위해 번호 풀을 성토/일반 두 시퀀스로 나눴는데, **수동 입력 번호의 중복 판정까지** 그 분리된 풀로 해버려 시퀀스를 넘는 충돌을 놓쳤다.

```text
대장에 일반 1,2,3 + 성토 3행 수동번호 1,2,3 (기본 정책 = 건너뛰기)
구 코드(efa0f0b^): dup, dup, dup  → 0건 등록 + "중복 3건" 경고
efa0f0b:          new, new, new  → 3건 등록, 번호 1·2·3이 각각 두 건
```

배치 내부만으로도 재현된다(논 `1` + 성토 `1`). **이 티켓이 없애려던 실패를 다른 문으로 다시 만든 것이다.**

### 왜 1차 리뷰가 놓쳤나
리뷰어의 차분 퍼징은 "미리보기 = 저장" 일치만 검증했다. 이 회귀는 **양쪽이 사이좋게 틀린** 경우여서 그 하네스로는 잡히지 않는다 — **구 코드와의 대조**가 필요했다.

### 올바른 의미를 어디서 찾았나
폼 등록 경로가 기준이다 — `soil-script.js:2038-2043`의 중복 검사는 `logBaseNumber === numToCheck`로 **subCategory를 보지 않는다.** 즉 **시퀀스 분리는 채번에만 해당하고 중복 판정에는 해당하지 않는다.** 자의적 재설계가 아니라 앱의 확립된 규칙을 따랐다.

### 수정 (`62145b1`)
- 자동채번: 두 시퀀스 분리 유지 (`efa0f0b`의 본 수정 — 그대로 옳다)
- 수동 번호 중복: `collectLiteralNumbers` 신규 — **표기 그대로, 시퀀스 통합** 비교
- 자동부여 번호도 표기 집합에 넣어 뒤따르는 수동 행이 충돌을 감지
- `F5`와 `5`는 표기가 달라 여전히 충돌하지 않음 (**과잉수정 방지 테스트 포함**)

**부수 효과**: F 접두 수동 번호가 중복을 빠져나가던 기존 결함도 닫혔다 — 구 코드는 일반 풀에서 F를 제외해 `pool.has('F5')`가 구조적으로 항상 false였다(1차 리뷰 P1).

**구조적 방지**: 세 풀 중 하나를 빠뜨리면 그 검사가 조용히 사라진다 — 이번 회귀가 정확히 그 형태였다. `computePreview`가 `logs`를 받아 세 풀을 **내부에서 도출**하게 바꿨다.

## 재리뷰 지적 반영 (`e16bb7b`)

재리뷰는 APPROVED였으나 MINOR 중 **저장 번호 정합성을 깨는 1건은 별 티켓으로 미루지 않았다** — 이 티켓이 지키려는 불변식이기 때문이다.

`seenPool.add(key)`가 `willBeSaved` 게이트 밖에 있어 저장되지 않는 행의 번호가 배치 집합에 남았다:

```text
대장 F1(성토)·2(일반) / 배치 [성토 수동 '2'(→건너뜀), 성토 자동]
수정 전: 미리보기 F3, 매니저 실제 부여 F2   ← 미리보기 ≠ 저장
수정 후: 미리보기 F2, 매니저 실제 부여 F2
```

함께 반영한 저비용 지적:
| 항목 | 조치 |
| --- | --- |
| `logs` 비배열 시 검사가 조용히 사라짐 | `logWarn`으로 드러낸다 |
| `_existingNumbers()` dead code | 제거 — 회귀를 유발한 "풀을 하나씩 넘기는" 진입점이 그대로 보였다 |
| 기본 경지구분 폴백 비대칭 | `collectExistingNumbers`에 폴백 추가 (계약에서 유일하게 어긋난 줄) |
| 회귀 단위 7건이 배선 미검증 | `logs` 전달로 전환 — 의미와 도출 경로를 함께 덮는다 |

### E2E 단정 방식을 특히 신경 썼다
이 결함은 형제 프로젝트에서 **75건이 전부 통과하는 상태로 새어나갔고** 원인이 약한 단정이었다:
- 저장 확인이 메모리 배열만 읽어 `saveLogs()`를 no-op으로 만들어도 통과
- 접수번호 단정이 `not.toBe('')`뿐이라 전 레코드에 `'1'`을 넣어도 통과

그래서 새로고침 후 `localStorage`를 읽고 **유일성과 실제 번호값을 정확 일치**로 단정한다. 기존 5건이 전부 자동채번이라 수동 번호 경로를 밟지 않았다는 공백도 재리뷰가 지적해 케이스를 추가했다.

## 이 티켓에서 배운 것

**1차 코드리뷰 APPROVED가 안전을 뜻하지 않았다.** 16,000회 퍼징을 돌린 리뷰가 통과시킨 커밋에 회귀가 있었고, 그것을 잡은 것은 "이 변경을 반증하라"는 적대적 레인이었다. 두 레인이 보는 것이 다르다 — 전자는 새 코드의 내부 정합성을, 후자는 **구 코드와의 차이**를 본다.

그리고 이 결함의 근본 원인은 로직 오류가 아니라 **테스트할 수 없는 구조**였다. 채번 계산이 모달 상태에 묶여 있어 어떤 단정도 걸 수 없었고, 그래서 결함이 오래 살아남았다. 순수화가 이번 수정의 절반이다.

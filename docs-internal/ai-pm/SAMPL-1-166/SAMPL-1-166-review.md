# SAMPL-1-166 코드 리뷰 — 접수번호 중복이 클라우드 병합으로 새어 들어온다

## 실데이터가 원인을 드러냈다

SAMPL-1-165로 상세를 보이게 하자 담당자 화면에 이것이 나왔다.

```text
농가의뢰 328 — 2건 (박성권/밭/2026-03-11 #108e3c0d,  박성현/밭/2026-03-11 #9174bba3)
농가의뢰 329 — 2건 (박성권/과수/2026-03-11 #5b69687b, 박성현/과수/2026-03-11 #763e2743)
농가의뢰 330 — 2건 (박성권/과수/2026-03-11 #24c808e1, 박성현/과수/2026-03-11 #f986debd)
```

**우연이 아니다.** 같은 날, **연속 번호 3개**, **필지 구성까지 동일**(밭·과수·과수).
`328·329·330`은 `const num = baseNumber + index`로 **필지 3개짜리 한 접수**가 받는
번호다(`soil-script.js:2289`). 다필지 접수 한 건 분량의 번호가 **통째로 두 번** 나갔다.

## 원인이 두 겹이다

**① 등록 시 중복 검사가 로컬만 본다.**

```js
const latestLogs = SampleUtils.safeParseJSON(yearStorageKey, []);   // soil-script.js:2253
```

다른 기기·창에서 먼저 접수돼 아직 동기화되지 않은 건은 보이지 않는다.

**② 병합이 번호 유일성을 검사하지 않는다.**

`smartMerge`는 **id 기준**이다(`sync-utils.js:54`). 번호는 **정렬에만** 쓴다(`:147`).
id가 다르고 번호가 같은 두 레코드는 **둘 다 조용히 살아남는다.**

접수번호는 **분석결과 매칭 키**다. 같은 번호가 둘이면 어느 시료의 결과인지
확정할 수 없고, 라벨·흙토람 내보내기·대장 출력도 어긋난다.

## 무엇을 했나 — B안(병합 시점 탐지)

세 선택지 중 **B**를 택했다.

| 안 | 내용 | 판단 |
| --- | --- | --- |
| A | 등록 직전 Firestore 확인 | **보류** — 오프라인에서 등록이 막히거나 느려진다. 이 앱은 오프라인 우선 설계다 |
| B | **병합 시점 탐지 + 알림** | **채택** — 등록을 막지 않아 설계를 해치지 않는다. 다만 사후 발견이다 |
| C | 기기별 번호 대역 분리 | **보류** — 접수번호 체계 변경이라 담당자 확인이 필요하다(이미 종이·엑셀에 쓰였다) |

`findReceptionConflicts` 순수 함수를 만들고, `smartMerge`가 결과에 실어 보내며,
매니저가 토스트로 알린다.

## 독립 리뷰 레인

- **gemini: 미수행** — `GOOGLE_CLOUD_PROJECT` 미설정. **실행하지 않은 검증을 통과로 적지 않는다.**
- **codex: 수행** — CRITICAL 0 / **MAJOR 2** / SUGGESTION 1

### MAJOR 1 — 알림이 **정작 가장 흔한 경로에서 울리지 않았다**

`loadYearData()`는 `mergeCloudData()`를 쓰면서 `merged.data`만 읽고
`notifyReceptionConflicts()`를 부르지 않았다. `syncWithCloud()` 경로만 알렸다.

**담당자가 실제로 겪는 것은 첫 화면 로드다.** 즉 B안의 핵심이 빠져 있었다 —
내 수정이 목표를 빗나갔다.

→ `loadYearData`의 병합 직후에 알림을 붙이고, **그 경로를 태우는 E2E**를 새로 썼다
(Firebase를 스텁해 실제 `loadYearData`를 통과시킨다).

### MAJOR 2 — 고친 뒤의 **재발을 영원히 침묵**시킨다

억제 키가 `경지구분/번호`뿐이었다. 담당자가 고친 뒤 **다른 레코드가 같은 번호로
다시 겹쳐도** 같은 키라 알림이 나오지 않는다.

**재발을 놓치는 것이 이 기능이 막으려는 바로 그 실패다.**

→ 억제 키에 **충돌한 레코드 id**를 포함시켰다(정렬해서 병합 순서에 흔들리지 않게).

### SUGGESTION — B안은 발견책이지 재발 방지책이 아니다

리뷰의 판단에 동의한다. 알림을 무시하거나 오프라인이 지속되면 중복은 계속 생긴다.
**A안 없이는 강한 의미의 재발 방지가 불가능하다.** 다만 A안은 오프라인 우선 설계와
충돌하므로 담당자 판단이 필요하다 — 티켓에 세 선택지를 남겼다.

리뷰가 **정상이라고 확인한 것**: `5-1`과 `5-1`의 정확한 중복은 잡고 `5`와 `5-1`은
잡지 않는다(서브넘버는 정상적으로 별도 레코드다), `F5`·숫자/문자열 혼용도
`String()` 정규화로 잡힌다, `smartMerge` 반환 형태 변경이 기존 호출부를 깨지 않는다
(`BaseSampleManager.smartMerge`가 배열로 언래핑한다).

## 남은 한계

- **B안은 사후 발견이다.** 등록을 막지 않으므로 중복은 계속 생길 수 있고,
  알림을 무시하거나 오프라인이 지속되면 놓친다. **A안/C안은 담당자 판단 대기다.**
- **억제는 세션 범위다.** 앱을 다시 켜면 같은 충돌을 다시 알린다 — 고치기 전까지는
  계속 보이는 편이 낫다고 판단했으나, 성가시다면 조정 여지가 있다.
- 이 탐지는 **병합이 일어날 때만** 돈다. Firebase가 꺼져 있으면 병합이 없어
  탐지도 없다 — 그때는 설정 화면의 정합성 점검이 유일한 수단이다.
- 등록 시 중복 검사가 로컬만 보는 문제(원인 ①)는 **그대로 남아 있다.** B안은
  ②를 드러낼 뿐 ①을 고치지 않는다.

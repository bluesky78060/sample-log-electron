# SAMPL-1-168 코드 리뷰 — 수정 경로의 접수번호 중복 검사

🔴 CRITICAL: 0건 / 🟠 MAJOR: 1건 (수정 완료) / 🟡 MINOR: 0건 / 🔵 SUGGESTION: 2건 (반영)
→ 판정: APPROVED

## 무엇이 없었나

SAMPL-1-167 독립 리뷰가 "그룹 수정은 클라우드 확인을 우회한다"고 지적했다.
확인해 보니 그보다 컸다.

```bash
grep -c "duplicateNumbers" src/soil/soil-script.js   # → 3, 전부 신규 등록 분기
```

수정 경로에는 **로컬 검사조차 없었다.** 기존 접수를 열어 접수번호를 이미 있는
번호로 바꾸면 아무 경고 없이 저장됐다. 접수번호는 분석결과 매칭 키라,
겹치면 어느 시료의 결과인지 확정할 수 없다.

## 설계 — 자기 제외가 이 티켓의 전부다

수정은 **자기 번호를 그대로 다시 쓰는 것이 정상**이다. 신규 등록의 검사를 그대로
붙이면 아무것도 바꾸지 않은 저장조차 막히고, 담당자에게는 앱이 고장난 것과 같다.

자기 제외는 **두 갈래**이고 둘 다 필요하다:

| 갈래 | 이 갈래만 살리는 경우 |
| --- | --- |
| `ids` (편집 중인 id) | `groupId`가 없는 옛 레코드 |
| `groupId` | 다른 자리가 같은 그룹에 추가해 `editingGroupIds`에 없는 레코드 |

`groupId`가 빈 값이면 제외 기준으로 쓰지 않는다 — 안 그러면 groupId 없는 레코드가
전부 제외돼 **검사가 통째로 무력화된다.**

신규 등록과 달리 **자동 재부여하지 않는다.** 이미 접수된 건의 번호를 말없이 바꾸면
분석결과 매칭 키가 어긋난다 (라벨·흙토람 내보내기·대장 출력도 이 번호를 쓴다).

## 독립 리뷰(codex)가 잡은 것 — 제 판단이 틀렸다

🟠 **MAJOR — 단일 수정 경로를 잘못된 근거로 범위에서 뺐다.**

`collectCommonFormData()`에 `receptionNumber`가 없는 것을 보고 "단일 수정은 번호를
못 바꾼다"고 판단했다. 그러나 그 아래에서 **다시 읽고 있었다**:

```js
const updatedLog = {
    ...existingLog,
    ...this.collectCommonFormData(formData),
    receptionNumber: formData.get('receptionNumber'),   // ← 여기
```

브랜치의 앞부분과 신규 등록 구간만 읽고 중간을 건너뛴 탓이다. 단일 수정에도 같은
검사를 넣었고, 하위번호(`5-1`)로 열렸을 때를 위해 기준번호로 정규화한다 —
풀 쪽은 기준번호로 비교하므로 한쪽만 원문이면 겹침을 통째로 놓친다.

🔵 SUGGESTION 2건 반영: F번호·하위번호 경계 테스트 추가, 단일 경로 테스트 추가.

## 변이 검증 — 6종 전부 검출

| 변이 | 결과 |
| --- | --- |
| A. `ids` 자기 제외 제거 | `groupId 없는 옛 접수도 자기 번호로 저장된다` 실패 |
| B. `groupId` 자기 제외 제거 | `다른 자리가 같은 그룹에 추가한 레코드는 충돌이 아니다` 실패 |
| C. 그룹 검사 무력화 | 차단 테스트 2건 실패 |
| D. 클라우드 풀 병합 제거 | `클라우드에만 있는 번호로 바꿔도 막는다` 실패 |
| E. 단일 검사 무력화 | 3건 실패 |
| F. 기준번호 정규화 제거 | `하위번호(5-1)로 열려도 기준번호로 비교한다` 실패 |

⚠️ A와 B는 **처음에 검출되지 않았다.** 두 제외가 서로를 가려 어느 쪽도 죽은 코드로
보였다. 각 갈래만 유일하게 필요한 상황을 테스트로 세운 뒤에야 검출됐다.
"통과했다"가 "검증했다"가 아님을 그대로 보여준다.

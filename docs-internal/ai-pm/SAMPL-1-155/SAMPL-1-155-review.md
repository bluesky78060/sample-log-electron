# SAMPL-1-155 코드 리뷰 — 성토 접수번호 손상 데이터 조회

## 티켓 1단계를 내가 직접 실행할 수 없었다

이 티켓은 **운영 점검**이다. 1단계는 "브라우저 콘솔 또는 설정 화면에서 손상 여부 조회"인데,
그 데이터는 **담당자 기기의 localStorage/Firestore에만** 있다. 내가 실행할 방법이 없다.

그래서 티켓 3단계(권장)로 적혀 있던 **설정 화면 정합성 점검 도구**를 만들었다.
1단계를 담당자가 한 번의 클릭으로 수행할 수 있게 하는 것이 이 티켓을 진짜로 진행시키는
유일한 길이었다. 재발 탐지(3단계)도 함께 해결된다.

**2단계(재번호)는 하지 않았다.** 티켓이 "손상이 없을 가능성이 높으므로 재번호 스크립트를
미리 만들지 않는다"고 못 박았고, 실제 조회 결과를 보기 전에는 만들 근거가 없다.

## 도구는 찾기만 하고 고치지 않는다

접수번호는 라벨·흙토람 내보내기·대장 출력에 **이미 쓰였을 수 있다.** 도구가 조용히
재부여하면 종이와 화면이 어긋난다. 화면에도 "이 도구는 고치지 않습니다"라고 적고
E2E가 그 문구를 단언한다.

## 검사 항목

| 유형 | 왜 문제인가 |
| --- | --- |
| 성토인데 F 접두 없음 | 일반 시퀀스 풀에서 제외돼 **새 일반 접수가 같은 표기를 받는다** (SAMPL-1-153 손상 데이터의 모습) |
| F 접두인데 성토 아님 | 두 시퀀스 어디에도 안 보이는 **유령 번호** |
| 소문자 f로 시작 | `parseInt('f3')`가 NaN이라 채번 커서에 반영되지 않는다 |
| 형식 아님 | 정렬·채번·중복 판정이 전부 어긋난다 |
| 같은 경지구분 안 중복 | 채번이 경지구분 단위로 독립이므로 그 범위에서 본다 |

**분류는 배타적이다.** 처음에는 형식 검사를 독립으로 뒀는데 `f3`이 두 곳에 계상돼
4건짜리 데이터가 "5건 확인됨"으로 보고됐다 — **E2E가 잡았다.** 숫자가 실제 건수와
다르면 담당자가 목록과 대조할 수 없다. 우선순위는 고칠 수 있는 순서다:
소문자 f → 형식 → F 불변식.

## 독립 리뷰 레인

- **gemini: 미수행** — `GOOGLE_CLOUD_PROJECT` 미설정. **실행하지 않은 검증을 통과로 적지 않는다.**
- **codex: 수행** — MAJOR 1 / MINOR 1 / SUGGESTION 1 + "테스트에 없는 경우" 지적

### codex 지적과 대응

| 심각도 | 지적 | 대응 |
| --- | --- | --- |
| MAJOR | **CSV 인젝션** — 선행 `\t`·`\r`·`\n`을 막지 않는다. Excel이 앞의 탭을 지우면 뒤의 `=`가 수식으로 살아난다 | 가드를 `/^[\t\r\n=+\-@\|]/`로 넓혔다 |
| MINOR | `issueCount` 단위 불일치 — 중복을 "1종"으로 세는데 CSV에는 2줄이 나와 대조할 수 없다 | `중복 번호 1종(2건)`으로 영향 레코드 수를 함께 적는다 |
| SUGGESTION | 소문자 f는 형식 검사를 거치지 않으므로 `fabc`는 대문자로 고쳐도 형식이 틀리다 | 문구에 "대문자로 고친 뒤 형식 재확인"을 넣었다 |
| (지적) | 손상 JSON·**레거시 키**·탭 수식 케이스가 테스트에 없다 | 세 경우를 모두 테스트로 덮었다 |

### 리뷰가 유도한 가장 중요한 발견 — 레거시 키

"레거시 키" 언급을 확인하다 **내 코드가 연도 없는 `soilSampleLogs` 키를 통째로
건너뛰고 있음**을 찾았다. `cache-manager.js:24`가 그 키의 존재를 명시한다.

```js
const m = key && /^soilSampleLogs_(\d{4})$/.exec(key);   // 레거시 키를 못 잡는다
```

레거시 데이터가 있는 기기에서 이 도구는 **그 데이터를 검사하지 않고 "문제 0건"이라고
말했을 것이다.** 이 점검이 막으려는 바로 그 조용한 실패를 점검 도구 자신이 저지르고
있었다. E2E로 고정했다.

### 손상 JSON도 조용히 넘기지 않는다

`JSON.parse` 실패를 빈 배열로 흘리면 "문제 0건"이 거짓이 된다. 읽지 못한 저장소를
**결과보다 먼저** 빨간 상자로 알리고, E2E가 그것을 단언한다.

## 남은 한계

- **1단계 조회 결과는 아직 없다.** 도구를 만들었을 뿐이며, 실제 손상 여부는
  담당자가 설정 화면에서 실행해야 알 수 있다. **이 티켓의 원래 질문("손상이 있는가")은
  여전히 답이 없다.**
- **Firestore는 범위 밖이다.** 티켓이 Firestore 확인도 언급했으나 이 도구는
  localStorage만 훑는다. 오프라인 우선 구조라 localStorage가 사본을 갖지만,
  로컬에 없는 연도가 클라우드에만 있으면 놓친다.
- **2단계(재번호)는 미착수.** 조회 결과를 보고 담당자가 판단할 일이다.
- `soil-result-importer.js`의 CSV도 같은 인젝션 구멍(`=+-@|`만 검사)이 있다.
  이번에 새로 쓴 쪽만 넓혔다 — 그쪽 정리는 별건이다.
- 토양 외 4개 시료 타입은 검사하지 않는다. 이 불변식은 토양 성토 번호에만 있다.

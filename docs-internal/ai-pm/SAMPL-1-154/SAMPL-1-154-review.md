# SAMPL-1-154 코드 리뷰 — 서브넘버 행이 '중복'으로 조용히 버려짐

## 무엇이 문제였나

접수번호에 `5`, `5-1`, `5-2`가 들어오면 두 번째부터 "중복"으로 판정돼
기본 정책(건너뛰기)에서 **사라졌다.** 사용자에게는 `⚠️ 중복 2건`으로만 보여
**정상 동작으로 오해**한다 — "중복 제거가 잘 됐다"고 읽히는 것이 가장 위험했다.

근본 원인은 중복 판정이 **본번만** 비교한 것이다.

```js
const base = recNo.split('-')[0].trim();            // '5-1' → '5'
const isDup = existingLiteral.has(base) || seenLiteralInBatch.has(base);
```

`collectLiteralNumbers`도 저장된 번호를 같은 방식으로 접어 넣고 있었다.
그래서 `5-1`이 본번 `5`를 점유하고, 뒤따르는 `5-2`가 그 `5`와 충돌했다.

## 방향 결정 — 담당자 확인 (2026-08-20)

`-N` 접미사는 이 저장소에서 **두 가지**를 뜻한다. 코드에 이미 그 충돌이 경고돼 있다
(`soil-script.js:2054-2069`):

```text
분할모드 = 한 지번에 작물 여럿 → 321, 321-1
하위필지 = 한 접수에 지번 여럿 → 321-1, 321-2
둘이 동시에 일어나면 같은 번호가 두 가지를 뜻하게 된다.
⚠️ 접수번호는 분석결과 매칭 키이므로 이 규칙을 바꾸려면 다시 확인을 받아야 한다.
```

그리고 **대장 내보내기는 하위필지 쪽으로 쓴다** (`soil-script.js:4856`):

```js
'접수번호': `${log.receptionNumber}-${sIdx + 1}`,   // 하위필지 행
'필지 주소': subLotAddress,                          // ← 각자 다른 지번
```

즉 내보냈다 다시 가져오면 정확히 이 티켓의 입력이 나오는데, 그것은 작물이 아니라
**하위필지**다. 그래서 담당자 확인을 받아 **지번주소로 판별**하기로 했다.

| 같은 본번 그룹 안에서 | 의미 | 저장 형태 |
| --- | --- | --- |
| 지번주소가 **같음** | 분할모드 | 작물마다 레코드 1개, `groupId` 공유, `cropIndex` 0,1,2 |
| 지번주소가 **다름** | 하위필지 | 접수 1건, `parcels[0].subLots[]` |

**본번 행(`5`)이 배치에 있을 때만 묶는다.** `5-1`, `5-2`만 온 파일은 의도를 알 수 없어
추측하지 않고 각자 원문 번호로 등록한다 — 이 티켓의 목적은 "묶는 것"이 아니라
**조용한 유실을 없애는 것**이다.

## 리뷰 전에 스스로 찾은 것

**그룹 id가 `imp-5` 형태라 가져오기끼리 충돌한다.** 미리보기 안에서 행을 묶는 키일
뿐인데 그대로 저장하면, 다른 날 다른 경지구분에서 같은 본번이 나올 때 **무관한 두
접수가 같은 `groupId`**를 갖고 그룹 수정이 둘을 한 접수로 연다.
→ `_commit`이 실행마다 진짜 UUID로 해석하도록 고치고 E2E로 고정했다.

codex가 **정상이라고 확인한 것**도 기록해 둔다: `collectLiteralNumbers`의 `split` 제거가
기존 중복 판정을 약화시키지 않는다는 점, 본번 행이 없거나 둘 이상일 때 묶지 않는
보수적 처리, `new + sub` 경로에서 `willImport`와 `_commit`이 일치한다는 점.

### codex 2라운드 — 수정본 재리뷰

> 규칙: **찾은 쪽과 고친 쪽이 다르면 수정본을 다시 리뷰에 넣는다.**

1라운드 수정본을 그대로 다시 넣었더니 **또 MAJOR가 나왔다** — 규칙이 경고하는 그대로다.
판정 **CHANGES_REQUESTED** (CRITICAL 0 / MAJOR 1 / MINOR 1).

| 심각도 | 지적 | 대응 |
| --- | --- | --- |
| MAJOR | **`subLots` 후처리가 O(n²)**. 선두마다 `items` 전체를 `filter`한다. "1만 그룹 × 2만 행"이면 2억 회 비교 — 대량 가져오기에서 화면이 멎는다. `PREVIEW_ROW_LIMIT`은 그리는 행만 제한하고 계산량은 줄이지 않는다 | 그룹별 Map에 담는 **단일 순회**로 바꿨다. 30그룹 × 3행 케이스로 묶임 결과가 규모와 무관함을 고정 |
| MINOR | 주소 컬럼이 **매핑됐지만 값이 빈** 경우도 `'' === ''`로 "같아 보여" 분할모드로 오판한다. 매핑 부재만 막았지 빈 값은 못 막았다 | 선두나 follower의 주소가 비면 묶지 않는다 |

2라운드가 **정상이라고 확인한 것**: `buildSubNumberGroups`에서 `subLots`를 뺀 뒤에도
`subLots`가 `undefined`인 채 새어나가는 경로는 없다(후처리가 반환 전에 항상 돈다).
`_commit`의 `resolveGroupId`는 `_recompute`와 어긋나지 않는다(`imp-*`는 미리보기 내부
키로만 쓰이고 커밋마다 안정적으로 UUID가 된다).
`dup`+덮어쓰기 follower가 자기 레코드로 저장되고 선두 `subLots`에서 빠지는 것도
현재 UI 계약("그래도 추가")과 일관된다 — 기존 레코드 병합은 SAMPL-2-30 ②의 몫이다.

| --- | --- |
| 빈 주소 가드를 제거한다 | 단위 **1건 실패** |
| 단일 순회 후처리에서 `status === 'sub'` 조건을 뺀다 | 단위 **1건 실패** |

## 변이 검증이 내 코드의 죽은 부분을 잡았다

면적 전달을 없애는 변이를 걸었는데 **59건이 그대로 통과**했다. 원인은 후처리가
`subLots`를 통째로 덮어써서 `buildSubNumberGroups`의 면적 코드가 **도달하지 않는
죽은 코드**였기 때문이다. 겉보기엔 면적을 다루는 것처럼 보이지만 실제로는 아무 일도
하지 않는다 — 나중에 누가 그 줄을 믿고 고치면 아무 효과가 없다.

죽은 코드를 지워 출처를 하나로 만든 뒤 다시 변이를 걸자 정상 검출됐다.

| 변이 | 결과 |
| --- | --- |
| 중복 비교 키를 `literal` → `base`로 되돌린다 (원래 결함) | 단위 **4건 실패** |
| 지번주소 판별을 없애 항상 `split` | 단위 **1건 실패** |
| `collectLiteralNumbers`를 다시 접는다 | 단위 **2건 실패** |
| `subLots` 후처리(건너뛴 행 제외)를 없앤다 | 단위 **1건 실패** |
| 후처리의 면적 전달을 없앤다 | 단위 **1건 실패** |
| 지번주소 미매핑 가드를 없앤다 | 단위 **1건 실패** |
| 매니저의 면적 파싱을 `'0'` 고정으로 되돌린다 | E2E **1건 실패** |

7종 전부 검출.

## E2E를 처음 썼을 때 아무것도 검증하지 않았다

작성한 E2E가 통과하지 못해 들여다보니, **"접수번호 자동부여"가 기본 켜짐**이라
엑셀의 접수번호를 아예 쓰지 않는 경로(`autoAll`)로 빠지고 저장 번호가 `1`, `2`로
나왔다. 체크 해제를 넣어야 검증하려던 경로에 도달한다.

이걸 놓쳤다면 **초록불인 채로 아무것도 검증하지 않는 테스트**가 됐을 것이다.
헬퍼에 사유를 주석으로 남겼다.

## 기존 테스트가 결함을 계약으로 못 박고 있었다

`'서브넘버는 본번으로 접고 경지구분 범위를 지킨다'`가 옛 동작을 고정하고 있었는데,
그 동작이 바로 이 버그였다. 계약을 바꾸고 **왜 바꿨는지**를 테스트 주석에 남겼다.

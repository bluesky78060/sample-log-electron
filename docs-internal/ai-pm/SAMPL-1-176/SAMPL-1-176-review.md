# SAMPL-1-176 코드 리뷰 — 퇴비 목록 열 폭 안정화

## 요청

> "퇴비 목록에도 같은 열 폭 수정 넣어줘"

SAMPL-1-174(토양)와 같은 증상을 퇴비에 이식했다.

## 실측 — 재현 확인

`.data-table`이 `width: 100%`라 **표가 화면보다 좁으면** 남는 폭을 모든 열이 나눠 갖는다.
전체 보기로 숨김 열 셋(법인여부·생년월일/법인번호·우편번호)이 드러나면 나머지가 전부 양보한다.

| 화면 폭 | 표 vs 화면 | 폭이 바뀐 열 | 최대 |
| --- | --- | --- | --- |
| 1280px | 표가 넓다 (2093 > 1238) | **0개** | — |
| 2200px | 살짝 좁다 | 7개 | −37.0px |
| 2560px | 좁다 (2518 포트) | **14개** | −33.5px |

## 수정

```css
.compost-navbar ~ .main-content .col-farm-address {
    width: 100%;        /* 250px → 100% */
    min-width: 250px;   /* 유지 */
    /* max-width: 250px 제거 */
}
```

적용 후:

| 화면 폭 | 폭이 바뀐 열 |
| --- | --- |
| 1280px | **0개** (예전과 동일) |
| 2200px | **1개** — 농장주소 315.2 → 250 |
| 2560px | **1개** — 농장주소 675.2 → 399.5 |

### `max-width`를 지운 이유는 흡수가 아니다

**표 셀의 `max-width`는 열 폭의 상한으로 작동하지 않는다.** CSS 2.1은 table-cell의
`min-width`/`max-width` 효과를 정의하지 않고(§10.4), 열 폭은 자동 표 레이아웃이 셀의
`width`를 최소 폭 계산에 넣은 뒤 남는 폭을 분배해 정한다(§17.5.2.2).

필요한 변경은 `width` 하나다. `max-width`를 지운 것은 **아무 일도 하지 않는 선언이
남아 있으면 다음 사람이 "250인데 왜 더 넓지?" 하고 헤매기 때문**이다.

> 자매 저장소 SLS-1-282가 실측으로 밝힌 사실이다. 그 전 티켓(SLS-1-279)은 이 오해 때문에
> 퇴비를 아예 범위에서 뺐었다 — **독립 리뷰의 지적을 실측 없이 받아들인 결과**였다.
> 그래서 이번 변이 검증은 처음부터 `max-width`가 아니라 `width`로 걸었다.

### `min-width: 250px`를 남긴 이유

표가 화면보다 넓으면 받을 남는 폭이 없어 250px에 머문다 — **좁은 화면에서는 예전과
완전히 같다**(1280px 실측 변동 0개). "표를 밀지 않는다"는 원래 설계 의도가 지켜진다.

주소(`col-address`)는 250px 고정으로 남겼다. **흡수 열은 하나여야** "한 열만 변한다"는
목적이 선명하다.

## 독립 리뷰 (codex)

```text
🔴 CRITICAL: 0건 / 🟠 MAJOR: 0건 / 🟡 MINOR: 2건 / 🔵 SUGGESTION: 0건
```

기능 변경 자체에는 지적이 없었다 — `min-width` 유지, 흡수 열 하나, 두 줄 표시 보존,
`.compost-navbar ~ .main-content` 스코프 격리, 인쇄·다크 모드 무영향, 2560px 선택의
타당성을 모두 확인해 주었다.

**MINOR 2건 모두 반영:**

1. **퇴비 시험이 폭 정착을 기다리지 않는다** — 토양 쪽 `waitForStableWidths`를 파일
   공용 헬퍼로 승격하고 표별 선택자를 인자로 받게 했다. 토양에서 실제로 이 문제를 겪었다
   (폰트 단계 로드 중에 재서 17개 열이 일제히 1.25배로 보고됐다).
2. **숨김 열 셋 중 하나만 확인한다** — `col-applicant-type`·`col-birth-corp`·`col-postcode`
   셋 모두를 보는 `expectHiddenColumnsShown()`으로 바꿨다.
   함께 짚어 준 **fixture 필드명 불일치**도 고쳤다 — 렌더러는 `addressPostcode`·`birthDate`를
   읽는데 `postcode`·`birthCorp`로 넣고 있었다. 열은 그려지되 값이 `'-'`가 되어 시험이
   무엇을 보는지 흐려진다.

## 스스로 잡은 것 — 조용한 무효화

퇴비 표에는 `id`가 없어 `#logTableBody ~ thead th, table:has(#logTableBody) thead th`로
잡았는데, **앞쪽 선택자는 아무것도 매칭하지 않는다**(`thead`가 `tbody`보다 앞이라 `~`가
성립하지 않는다). 실측으로 확인했다:

```
combo: 25 / sibling: 0 / has: 25
```

죽은 선택자를 지웠고, 더 나아가 **매칭이 0이면 대기가 조용히 무효가 되는 위험**
(빈 문자열끼리 비교돼 즉시 "안정" 판정)을 헬퍼 안에서 끊었다.

## 변이 검증

⚠️ 변이는 `max-width`가 아니라 **`width`로** 걸었다 — SLS-1-282에서 `max-width` 변이가
아무것도 바꾸지 않아 "시험이 안 죽는" 음성 결과가 나온 선례가 있다.

| 변이 | 결과 |
| --- | --- |
| `width: 100%` → `250px` | '농장주소 말고는 폭이 그대로다' **FAIL** ✅ |
| `min-width: 250px` 제거 | '좁은 화면에서 250px에 머문다' **FAIL** ✅ |

두 시험이 각각 다른 규칙을 붙잡는다.

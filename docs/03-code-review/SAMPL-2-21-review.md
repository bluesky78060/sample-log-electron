## LOW-1 — 제목이 증명 범위보다 강했다 (반영)

실제로 증명하는 것: 이 스타일 객체를 프로덕션과 **같은 write 옵션**으로 돌리면

   **남은 한계를 주석에 명시**했다(닫으려면 export 메서드가 워크시트를 주입받아야 한다).

## LOW-2 — 앵커가 구조가 아니라 인접 텍스트였다 (반영)

`soilDataStyle()`이 `SRC.indexOf('applyHeaderStyles')`로 **첫 등장**을 찾았다.
지금은 호출부(`:1274`)가 걸리고 그게 흙토람 `dataStyle`(`:1682`)보다 앞이라 맞다.

그러나 앞쪽에 그 문자열이 든 주석이나 문자열이 생기면 **엉뚱한 것을 조용히 집는다**
(`objectLiteral`은 `at > -1`만 확인하므로 오류가 아니라 잘못된 값을 돌려준다).

→ 앵커를 **메서드 정의**(`applyHeaderStyles(ws, wsData) {`)로 좁혔다.
   뮤테이션으로 확인 — 앵커를 공익직불제 정의로 바꾸면 2건이 죽는다.

## 리뷰어가 짚은 강점

- 테스트 13이 "객체가 소스에 텍스트로 있다"에서 "이 객체를 실제 직렬화기에 통과시키면
  올바른 마크업이 나온다"로 옮겨간 것은 두 리뷰가 지적한 간극의 **실질적 일부**를 닫는다
- `package-lock` 처리가 옳다 — 무관한 esbuild 전이 의존성 드리프트를 문서/테스트 티켓에
  끼워 넣지 않았고 결과가 구조적으로 최소하다
- JSDoc 정정이 당연한 말을 반복하지 않고 **실제 사고 사례**를 근거로 경고를 더했다
- 이 파일의 주석이 문자열 스크래핑 방식의 한계를 과장 없이 적는다 — 좋은 테스트 위생

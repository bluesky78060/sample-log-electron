## 1. 목표 (Why)

사용자 신고: "목록에서 [수정]을 누르면 시료 번호 등 기본정보 수정이 안 되는 경우가 있다."

조사 결과 원인이 하나가 아니었고, 그중 일부는 **저장이 실패했는데도 성공 메시지가 뜨거나 아무 메시지도 없어서**
사용자가 실패 사실 자체를 인지할 수 없는 상태였다. 목표는 (a) 저장 실패를 유발하는 조건을 제거하고,
(b) 그래도 실패하면 반드시 사용자가 알 수 있게 만드는 것이다.

## 2. 사용자 (Who)

봉화군 농업기술센터 시료 접수 담당자. 접수 후 접수번호·성명·연락처 등 기본정보를 수정하는 일상 업무.

## 4. 제약

- 5개 시료 타입이 `BaseSampleManager`를 공유 → 공통 수정이 5개 화면에 동시 영향. 회귀 범위가 넓다.
- `setupYearSelection`은 **soil만 오버라이드**하므로 공통 수정이 soil에 자동 적용되지 않는다.
- `docs/`는 Vite `emptyOutDir` 빌드 산출물 → 빌드 시 이 문서들이 삭제됨. 빌드 후 재생성 필요.
- 테스트 프로젝트는 TypeScript로 분기되어 있어 이번 변경의 자동 동기화 대상이 아니다.

## 5. 우선순위

1. ② 가짜 성공 제거 (잘못된 성공 메시지는 데이터 유실을 은폐함 — 가장 위험)
2. ① 접수번호 덮어쓰기 가드 (사용자 신고 문구와 가장 직접적으로 일치)
3. ④ mailDate 유실 (조용한 데이터 손실)
4. ③ id 비교 정규화 (현재 id는 UUID 문자열이라 조건부 발생, 방어적 수정)

## 6. 리스크

- 연도 변경 시 `confirm` 추가 → 편집 중이 아닐 때도 확인창이 뜨면 일상 업무를 방해한다. 편집 중에만 물어야 한다.
- `mailDate` 보존을 `...prev` 전체 전개로 처리하면, 낡은 `samplingLocations` 배열 등이 남아
  다음 편집 시 잘못된 값이 표시되는 회귀가 생긴다(`water-script.js:442-455`가 해당 배열을 우선 참조).
  → 전체 전개가 아니라 **보존 대상 필드 명시** 방식으로 간다.
- `id` 비교를 String으로 완화하면 `'1' == 1` 류의 의도치 않은 매칭 가능성이 있으나,
  id는 UUID/타임스탬프 문자열이라 실질 충돌 위험은 없다.

## 7. 검증

- 수동 확인: 5개 시료 타입에서 목록 → 수정 → 저장이 정상 동작하는지
